# Правила облачной работы с AI Command Center

## Вход в задачу и источник состояния

1. Прочитать [текущий handoff](docs/STATUS.md), затем документы затронутого компонента.
2. Проверить `git status`, ветку, HEAD и актуальные GitHub PR/CI. Сохранять чужие
   незакоммиченные изменения. Отчёт или старый SHA не заменяет текущую проверку.
3. Определить разрешённый scope по текущему заданию владельца. История выполненных
   этапов и доступность инструментов не являются разрешением новых внешних действий.

Инструкции Stage 0A о documentation-only и PR в main были историческими.
Их исходный текст сохранён в [архиве](docs/history/AGENTS_STAGE_0A.md).
Позднейшие задания разрешили реализацию F1/F2/Telegram. Это уточняет контекст,
но не даёт постоянного неограниченного права менять код, серверы или проекты.
Полнота всей исторической переписки не предполагается; пробелы остаются явными.

## Ветка, реализация и PR

- Работать в отдельной ветке от проверенной базы текущей задачи. Пока реализация
  находится в не объединённой цепочке PR, не переходить на main, теряя предшественников.
  Базу нового PR выбирать по фактической зависимости, не назначать main автоматически.
- Не выполнять merge, retarget/закрытие чужих PR или deployment без отдельного
  разрешения. Не создавать дополнительные worktree без явного запроса владельца.
- Сохранять существующие архитектуру, F1 permissions, PostgreSQL/Outbox/Redis,
  lease/fencing, source pinning, verifier, broker и watchdog. Не создавать второй
  независимый механизм полномочий. Делать ограниченные обозримые изменения.
- Одно разрешение ограниченного этапа покрывает обычные edits/tests/bounded
  repairs/commits/PR в его рамках: [R-F1-AUTO-01](docs/requirements/AUTONOMOUS_EXECUTION.md).
  Не запрашивать каждую команду заново, но не обходить подтверждения платформы.
- После завершения задания сохранить результат и проверяемый handoff. Не считать
  следующий этап, платный вызов или внешнее подключение автоматически разрешённым.

## Проверки и доказательства

- Запускать проверки по затронутому scope; не отключать падающие проверки ради PASS.
  Основные команды и prerequisites — в [docs/STATUS.md](docs/STATUS.md).
- Контейнерные проверки требуют точных source/image revisions. Не менять label
  старого образа и не ослаблять pinning; собирать образ из соответствующего SHA.
- Итоговый CI сверять с финальным HEAD и его PR merge-ref. Повторные и пересекающиеся
  наборы не складывать. Различать passed, failed, skipped, not run и blocked.
- Mock AI/HTTP/PR не выдавать за настоящий AI-запуск или публикацию. Облачный
  rootful container test не подтверждает rootless/systemd/iPhone/VPS acceptance.
- При недоступности среды выполнять независимые проверки, сохранять checkpoint
  и точный блокер. После таймаута сначала сверять фактический результат операции.

## Серверы, секреты и расходы

- Опасные или необратимые операции требуют точного действия и версии,
  действующего срока разрешения и записи в журнале. Отсутствие ответа не согласие.
- Без отдельного конкретного разрешения не обращаться к VPS, не менять SSH,
  firewall, пользователей, daemons, service units, credentials или production.
  CRM VPS 206.223.246.79 не затрагивать. Не открывать публичную административную панель.
- Не отключать AppArmor, TLS-проверку или ограничения rootless Docker ради запуска.
- Состояние канала F33 сверять с датированным handoff и текущими доказательствами.
  Не объявлять неподтверждённый доступ действующим, не повторять старые
  bootstrap/install вслепую и не продлевать истёкшее окно.
  Сначала read-only reconciliation, затем новая точная разрешённая операция.
- Развёртывание использует существующие prepare/inspect/exact approval/install/
  postcheck/update interlocks. Не заменять их обычным compose up. Откат — только
  при подтверждённой совместимости с данными; независимые backup/stop сохраняются.
- Не публиковать ключи, пароли, токены, cookies, runtime secrets или клиентские
  данные в Git, чат, prompt, логи и артефакты. Использовать защищённую инъекцию
  доверенному сервису; исполнитель не получает credentials хоста или publisher.
- Реальные AI API, GitHub publisher, платные ресурсы и финансовые/торговые
  операции требуют отдельного разрешения. Лимит первого эксперимента 100 ₽ и
  ориентир 10 000 ₽/месяц сами по себе не разрешают расходы. Не придумывать тарифы.

## Другие проекты

Названия проектов, repository IDs, snapshots и очереди запросов — контекст,
не grants доступа или выполнения. Без отдельного задания не изменять их код,
ветки, PR, settings, CI, секреты и данные; не возобновлять их разработку автоматически.
CRM остаются самостоятельными системами, не переносить их production на VPS центра.
Capital Lab не получает права на реальные торговые операции из статуса проекта.

Политика и приоритеты владельца описаны в [handoff](docs/STATUS.md). При конфликте
исторической записи с новым заданием сохранять происхождение и реальные границы,
не выдавать устаревшую запись за текущее архитектурное решение владельца.
