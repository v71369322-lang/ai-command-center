## 2. Текущая архитектура

```text
Telegram owner
  -> telegram poller -> PostgreSQL: inbox, deliveries, audit
  -> voice process: local Whisper -> owner readback -> saved request
Private FastAPI/web -> PostgreSQL + Redis + technical F1/F2 commands
Redis/outbox -> worker -> runtime-broker -> separate rootless execution Docker
                         ^ independent watchdog + runtime-ledger SQLite
Codex/operator -> protected release/backup/reconcile tools + GitHub mailbox runner
Google Calendar: local draft/OAuth/sync contracts; live binding not found
```

На основном rootless daemon UID1000 восемь контейнеров проектаacc-f23:
PostgreSQL16, Redis7, FastAPI/web, Telegram, speech, worker, runtime-broker, watchdog.
Broker/watchdog имеют socket отдельного execution-daemon UID1001. Telegram и voice
Docker socket не получают. Изоляция уже реализована; речь не о доказанном
неограниченном AI-root доступе, а об отказе от всего контура разработки.

Стек: Python3.12+, FastAPI/Uvicorn, SQLAlchemy/Psycopg, PostgreSQL, Redis,
HTTPX, Cryptography/PyJWT. Dulwich и coding modules относятся к Git/разработке.
Отдельная speech-группа: faster-whisper1.2.1/CTranslate2/PyAV и локальный base-модельный
snapshot. Web собирается Node, отдельного постоянного frontend-контейнера нет.
Есть127 Python-файлов в command_center: существенная часть — coding, planning,
permissions, isolated runtime, publication, repair и operator lifecycle.

Работает acc-operations-runner.service (~115МиБ cgroup) и acc-operations.timer.
Есть исторические failed/transient apply units и активные fixed-prepare path units.
Они не доказывают текущую поломку deployment: оба текущих журнала VERIFIED.
Но это отдельный legacy operator surface, который нужно включить в вывод из эксплуатации.

**Другие проекты:** в rootful Docker этого же VPS работают семь контейнеров Capital Lab.
Их код, БД, volumes, Caddy/edge, backup timer, образы и процессы не включены в очистку.
CRM VPS206.223.246.79 не затрагивался. Не выполнять global Docker prune/system prune.

## 6. Почему нельзя просто остановить половину контейнеров

Worker использует Redis/broker socket; broker/watchdog разделяют runtime-ledger
иexecution Docker. API импортирует worker.broker и coding contracts; TelegramBridge
импортирует API.Command и многочисленные coding/planning handlers. Voice использует
TelegramBridge и PostgreSQL. Deployment manifest/validator жёстко требуют полный
набор сервисов и пять image keys. Backup/boot/postcheck тоже привязаны к этому набору.

Поэтому удаление services изcompose или файлов coding/* прежде отключения imports,
routes, permissions и изменения operator profile даст сломанный boot/backup,
а не Jarvis2. Запрет выполнения должен быть серверным и детерминированным, не только
просьбой модели или скрытием кнопки. Не давать LLM Docker/SSH/shell/Git publisher.

## 7. Предлагаемая минимальная архитектура

Три постоянно работающих контейнера после завершения перехода:

1. **assistant** — существующий Python/FastAPI: Telegram, typed domain services,
   короткий разговорный контекст, scheduler/reminders, calendar adapter, один AI-client.
   Handler сразу сохраняет входящее и отвечает receipt; долгие операции асинхронны.
2. **PostgreSQL** — единственная authoritative БД: projects, items, source messages,
   attachment metadata, decisions, schedules, durable jobs/outbox, action/budget evidence.
3. **speech** — существующее отдельное bounded CPU-распознавание, одна очередь/
   одна параллельная работа. Не тормозит Telegram event loop. При неиспользовании
   локальной ASR альтернативу обсуждать отдельно, не подключать платную автоматически.

Private attachment directory с квотой и согласованным retention, без отдельного
S3/векторного сервера на старте. Backup — фиксированный host timer/операторская
задача вне AI, не новый автономный агент. Redis и execution-daemon в целевой схеме
не нужны, но выводятся только после снятия зависимостей. Сначала допустимы пять
контейнеров (db,redis,api,telegram,voice), затем три: без рискованного одномоментного
слияния. Настройка restart/boot делается Codex, не самим Jarvis.

AI только понимает/структурирует/ищет/анализирует. Данные меняет небольшой набор
типизированных функций: создать/исправить/найти item, прочитать календарь, подготовить/
подтвердить событие. Авторизация owner, проверка версий, дедупликация, денежные лимиты
и разрешённые effects проверяются кодом независимо от ответа модели. Один основной
provider/model в конфигурации; более сложная маршрутизация — только при измеренной
необходимости. Существующие финансовые/idempotency механизмы переиспользуются после
отвязки от F1 execution, не копируются слепо вместе с Task/Approval/Fence зависимостями.
Новый Task приложения — не F1 Task запуска кода.

Пять направлений — категории контекста одного партнёра. Бизнес-источники остаются
отдельными системами; в Jarvis только требуемые summaries со ссылкой/периодом/свежестью.

## 8. Минимальная рабочая версия и дальнейший порядок

### Этап1: безопасное выключение developer-контура

После отдельного согласования этого плана:
- Подготовить точный release/remove manifest: ID/image digest/UID/unit/путь, owner,
  связи и rollback для каждого ресурса. Current956 и предыдущий проверенный9f сохранить.
- До изменений: свежий encrypted DB backup, schema/row counts, secure config/credentials
  recovery, release/git bundle, список mounts/volumes; отдельная копия вне VPS.
  Проверить checksum/decryption и реальное восстановление в отдельной среде.
- Ограниченный релиз отключает developer commands/routes/tools и новые F1 jobs;
  обычные сообщения/голос сохраняются. Проверить очереди/leases/финансовые UNKNOWN.
- Изменить штатный prepare/inspect/install/backup/boot/postcheck под assistant-only
  профиль, сохраняя exact pins/approval/backup/integrity interlocks. Не raw compose up.
- Выключить worker+broker+watchdog согласованным набором; затем только их operator
  units/runner/execution-daemon. Данные/учётные записи пока не удалять.
- Проверить Telegram, speech, текущие записи/напоминания и backup. Замер до/после.
- Отдельно предъявить точный список удалений и получить подтверждение. Лишь затем
  удалить ненужные образы/cache/копии, сохранив rollback и историю. Отчёт о фактических
  байтах/RAM/остановленных сервисах/удалённых runtime dependencies.

Результат этапа1: работающий приём без запуска разработчика, проверенный backup и
упрощённый runtime, а не обещание, что новый интеллектуальный UX уже готов.

### Этап2: завершённый пользовательский MVP

Вертикальные подэтапы, каждый можно использовать:
- 2A: один Inbox для текста/голоса -> несколько items (task/idea/note/reminder/event),
  project registry вPG, создание/редактирование/поиск/завершение обычной речью.
  Идея не становится обязательством; нет срока — хранить без срока. AI-классификация
  требует отдельно одобренных модели/лимитов/передачи данных. Без этого нельзя
  честно обещать универсальное понимание смешанного голосового сообщения.
- 2B: завершить OAuth и реальный Google adapter; получить расписание/свободные
  интервалы, создать событие по поручению, конфликты, напоминания. Если интеграция
  не пройдена на реальном аккаунте, весь календарный MVP не объявлять готовым.
- 2C: безопасное сохранение файлов/фото/скриншотов/документов/ссылок с оригиналом,
  metadata, пределами размера/форматов. OCR/извлечение содержимого только для
  поддержанных форматов; документы — данные, не команды. Голосовой ответ по запросу
  включается после выбора/проверки TTS и его затрат, не всегда включённая запись.

К концу этапа2 все эти сценарии должны работать, включая Google, не заглушки.
Сохранить существующие4 requests и архивные источники;9 developer Task не импортировать
как личные поручения. Статусы доменных задач: active/deferred/delegated/waiting/
blocked/completed. Responsible и заметки о делегировании не означают разрешение
посылать сообщения сотрудникам. Проекты создаются как данные; первоначальные шесть
направлений владельца. lnauto↔«Автосервис» сверить перед слиянием идентичностей,
а не предполагать автоматически. Старые IDs сохраняются как aliases.

Каждый исходник имеет стабильный ID/chat-update key и связанные items; классификацию
сохранять до исполнения эффектов, retries не создают новые записи/события. Исправления
«это идея, а не задача» применяются к конкретному item/revision и доступны для undo.
Сохранять оригинал по согласованной политике, а не только его AI-пересказ.

### Этапы3–6: после работающего MVP

3. Structured memory/Decision Log, утренний/вечерний/недельный и месячный обзор,
приоритизация и нагрузка. Факты с source/date/confidence, выборочный retrieval.
Начать с PostgreSQL/full-text+фильтров, не добавлять vector DB/Redis/граф на будущее.
При выявленной потребности смыслового поиска — отдельное измеренное решение.
Режимы normal/high-load/recovery/vacation ограничивают уведомления; все schedules
можно отключить. Нагрузка/энергия — по данным/самоотчёту, не диагноз и не обещание
«решить всё продуктивностью». Отсутствие данных не считается отсутствием прогресса.

4. Цели/занятия/привычки, библиотека, собственные размышления/цитаты, Mentor KB и
повторение. Пропуск дня не обнуляет достижения. Один каталог sources с допустимыми
материалами и точными ссылками/страницами. Различать цитату, извлечённый принцип,
интерпретацию Jarvis и его рекомендацию; не имитировать реальных наставников.
Их подходы сопоставлять, не догматизировать. Мысль дня — нечасто, без повторов,
только с проверяемой атрибуцией или явным «автор не подтверждён».

5. Ограниченные read-only adapters кCapital Lab/CRM. Не переносить их production/БД
в Jarvis. Каждая метрика имеет source, период, fetched_at и признак stale.
Доля в автосервисе: учитывать условия расчёта исходной системы и отдельно начислено/
фактически получено; не вычислять долю от произвольной выручки вместо чистой прибыли.
На этом аудите API соседних бизнес-систем не исследовались и доступ не расширялся.

6. Стратегические обзоры/аналитика — после появления достаточных достоверных данных.
Рекомендации конструктивно критичны: показать противоречие/компромисс/альтернативу,
признать неизвестное и оставить решение владельцу. Поддержка — по реальному прогрессу,
без лести, давления или вымышленных результатов. Это стиль одного помощника с
памятью, не пять агентов и не отдельный «mentor orchestration» сервис.

## 9. Проверка работоспособности

| Область | Критерий выхода |
| --- | --- |
| Сохранность | Before/after counts и stable source IDs совпадают; backup восстанавливается в отдельной БД; соседние проекты неизменны |
| Нет разработчика | Coding/execute/deploy/shell/publisher routes и tools недоступны; AI/файл не может их вызвать; нет mounts Docker socket/SSH/host credentials у assistant |
| Перезапуск | После согласованного service restart сообщения/очередь/jobs переживают перезапуск, readiness восстанавливается; reboot отдельно по разрешению, без остановки Capital Lab |
| Скорость | Предлагаемые SLO: durable receipt p95≤3с без ожидания AI; обычный поиск при нормальной нагрузке≤3с. Измерять, а не объявлять достигнутым |
| Голос | Реальная запись владельца -> readback -> одно сохранение; шум/ошибка/двойная доставка/длинный файл не теряют источник. Цель длинных записей до10мин проверить по ресурсам; нынешние120с/2000байт не считать достаточными |
| Inbox | Смешанное сообщение разделяется на несколько items, идея без срока, правка обычной речью, проекты добавляются без deployment |
| Google | Реальное чтение расписания и одно подтверждённое создание; timeout/retry/дубликат не создают второе событие; перенос/удаление без явного поручения требуют подтверждения |
| Напоминания | Учитываются owner timezone/quiet hours; одно уведомление, корректное повторное включение после перезапуска |
| Приватность | Чужой Telegram user отвергнут; prompt-injection вфайле не расширяет tools; данные вAI уходят только в согласованном объёме |
| AI расходы | До вызова разрешены provider/model/передаваемые данные/лимиты; после — учёт actual/UNKNOWN; нет автоматического увеличения лимита |
| Решения/память | Можно спросить «почему отказались от AI-разработчика» и получить исходное решение/причину, не выдуманную историю |

Не повторять тысячи F1-test cases как доказательство нового UX. Сохранить релевантные
security/idempotency/backup tests, архивировать developer-only CI после зависимости-
аудита. Полный старый CI проверял текущий код, не реализацию будущего Jarvis2.

## 10. Риски и восстановление

- **Удаление общей зависимости:** перед stop — dependency manifest и отключённый
  admission; сначала reversible disable, затем наблюдение, затем отдельное delete.
- **Смешение technical/personal Tasks:** additive domain schema, явный импорт,
  сохранение первичных источников, без переписывания старого audit.
- **Сломанный boot/backup после удаленияbroker:** отдельный assistant-only operator
  профиль до выключения старого набора. Сейчас шесть app-сервисов имеют restart=no;
  в проверенных acc*/user units нет подтверждённого boot/backup timer Jarvis. Два
  Docker daemons включены сlinger, но это не гарантия старта всех app-контейнеров.
- **Потеря сервера:** единственная локальная копия недостаточна. Backup38МиБ,
  последний04:09:42UTC; encrypted dump4,126,471байт иchecksum сейчас проверены.
  offsite_verifiedfalse; restore drill в этом аудите не делался. Нужны отдельная
  защищённая копия вне VPS, отдельное хранение ключа, проверенное восстановление.
- **Сломанный OAuth/дубли:** сохранятьsync ledger/стабильныеIDs/UNKNOWN reconciliation;
  выбрать владельца аккаунта/целевой календарь и минимально необходимые права.
- **AI ошибка/инъекция/утечка:** typed functions, validate-before-write, retrieval
  только owner scope, не давать shell, ограничения файлов и расходов, undo.
- **Стоимость/качество ASR/NLP:** текущий локальный speech сохранять, сравнивать на
  реальной речи; не покупать/переключать модели без разрешения. Тарифов и цены
  API этот аудит не устанавливает. Ранее названный баланс API не считается текущим подтверждённым балансом.
- **Rollback после новой схемы:** сначала additive migration и export, не обещать,
  что старый код понимает новые таблицы. Откат кода — только при совместимости;
  восстановление старой БД с потерей новых данных требует отдельного решения.
- **Длинная PR-цепочка:** закрепить live baseline956; переход вести от него,
  не от отставшего main. Консолидацию/merge/закрытие старых PR согласовать отдельно.

До удаления сохранять: current956+проверенныйpredecessor9f images/source/bundles,
конфигурацию и восстановительные материалы в защищённом месте. Код/rollback/schema
не смешивать с личными source attachments. Для контроля после очистки повторить
те же measurements по тем же UID, без суммирования shared Docker layers.

## 11. Решения и подтверждения

**Уже решено владельцем:** новая миссия, отказ от собственного AI-разработчика,
Codex как технический исполнитель, один интеллектуальный партнёр, read-only бизнес-
интеграции и последовательные этапы. Это не предлагается обсуждать заново.

**Сейчас нужно согласовать только план этапа1:** assistant-only профиль, отключение
developer admission/трёх execution services и Jarvis-owned операторского контура,
сохранение PostgreSQL/Telegram/voice/API и временноRedis, backup/restore gate и
замер результата. Конкретный release/SHA предъявляется после подготовки/проверок.

**Перед необратимой очисткой отдельно:** точный список IDs/путей/units/credentials,
срок rollback retention, свежая независимая копия и план восстановления. Образы,
данные, пользователи, secrets и старые PR сейчас не удаляются.

**Позднее, при соответствующем этапе:** provider/model/лимиты и разрешение платных
вызовов; объём private context вAI; retention/удаление оригиналов; Google account/
календарь/права/timezone; соответствие lnauto бизнесу автосервиса; расписание
уведомлений; ограниченные API grants дляCRM/CapitalLab. Не требовать все ответы
сразу и не подменять согласие доступностью старого API-ключа.
