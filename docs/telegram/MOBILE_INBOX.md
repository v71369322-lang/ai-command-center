## Поведение

После входа панель читает существующие owner-only GET
`/api/telegram/status` и `/api/telegram/requests`.
Она показывает отключённого бота, сохранённые запросы `NEEDS_PLANNING` и
отсутствие AI-планирования/голоса. Сохранённый запрос не объявляется
выполненной задачей. Никакие сообщения Telegram из браузера не отправляются.

Кнопка «Обновить Telegram» повторяет только чтение. Длинный текст переносится
на узком экране, HTML отображается обычным текстом. Если сервер вернул 404
(например, старый backend), 503, отказал в доступе либо прислал неизвестную
схему/режим, показывается ошибка этого раздела. Список не выдаётся за пустой,
бот не объявляется подключённым; остальные разделы панели продолжают работу.

Загрузка ограничена десятью секундами. Уход из раздела, выход из сессии или
смена credential отменяют незавершённые запросы и отбрасывают устаревшие
результаты. На экране Telegram нет поля для bot token, настроек подключения
или кнопки, снимающей запреты на внешние вызовы.

Серверная авторизация остаётся обязательной; скрытие элементов в браузере
не заменяет проверку роли на сервере. Данные владельца не показываются
оператору после смены сессии.

## Что эта работа не включает

Настоящего Telegram transport, фонового polling service, голоса и AI-планировщика
по-прежнему нет. Добавление токена само по себе не включает бота.
Токен нельзя передавать через чат, issue, PR, обычное поле панели или Git.
Для будущего включения нужны отдельно разрешённый защищённый secret binding
доверенного сервиса, проверенная привязка владельца и реальные тесты доступа.
Значения credentials в этой работе не запрашивались и не использовались.

Backend и схема БД не менялись относительно PR #21. Требование отдельной
проверенной миграции трёх Telegram-таблиц для старого VPS **сохраняется**;
эта UI-ветка не делает её F31 password-only update и не обходит deployment gate.
