# Статус задач с телефона

Облачное продолжение PR #24 (`a994de96c2f9656f1d766a849e63a6836e21ef65`).
Новая ветка `feat/telegram-task-status` сохраняет все зависимости #24 → #23 →
#22 → #21 → #20 → #17. Подготовленный F32-пакет остаётся закреплён за PR #24:
эта доработка не меняет его source pin и не доставляется на VPS автоматически.

## Что увидит владелец после отдельного подключения бота

| Команда | Результат |
| --- | --- |
| `/help` | Список доступных команд и напоминание об отключённом голосе/AI |
| `/tasks` | До пяти последних синтетических тестов текущего подключения |
| `/status UUID` | Состояние одного синтетического теста этого подключения |
| `/cancel UUID` | Существующее сохранение намерения отмены, не обещание мгновенной остановки |
| `/stop` | Существующая остановка новых запусков; не подтверждение остановки всех активных контейнеров |

Пример: после `/demo проверка связи` и предусмотренного подтверждения можно
скопировать UUID из карточки в `/status UUID`. Команды чтения не подтверждают
тест и не снимают остановку. Обычный текст продолжает сохраняться как
`NEEDS_PLANNING`, а не исполняться как бизнес-задача. Это ещё не интерфейс
управления настоящими CRM, распознавание речи или AI-планировщик.

Состояния объясняются по-русски: ожидание подтверждения, ожидание исполнителя,
выполнение, проверка, незавершённая отмена, отмена в записи задачи, ошибка,
блокировка безопасности и необходимость сверки. Истёкший/отсутствующий lease
не отображается как подтверждённое выполнение. `CANCEL_REQUESTED` не называется
завершённой отменой. Статус берётся из PostgreSQL, а не из свежего Docker inspect;
это не независимый мониторинг фактического процесса.

Успех требует совпадения SHA-256 артефакта и audit event `verified` от verifier,
с правильными task ID, fence и текущей source revision. Используется одна
проверка для уведомления результата и ответа на команду. Артефакт, параметры
задачи, произвольная причина ошибки и tool output в ответ не копируются.
Передаются только UUID, фиксированные объяснения и подтверждённый SHA-256.

## Полномочия и доставка

- Сохраняются owner/private-chat, secret-content, connection/revocation и leader
  guards существующего TelegramBridge/TelegramService.
- Доступны только owner `approved_render` задачи, связанные с DONE demo inbox
  текущего profile **и** точным F1 request key `owner:tg:<inbox ID>`. Один UUID
  или подмена `inbox.task_id` не открывает другой тест/веб-задачу/подключение.
- Неизвестная и недоступная задача дают один безопасный ответ без её данных.
- Команды не меняют Task, Approval, Outbox, admission, epoch или бюджет.
  Входящий запрос и исходящий ответ по-прежнему durable и аудируются.
- Повтор того же Update возвращает прежний снимок и тот же delivery intent;
  за свежим состоянием нужно отправить новое сообщение `/status UUID`.
- Чтение доступно при остановленных новых запусках, но нарушение audit chain,
  потеря PostgreSQL, leadership или отзыв подключения блокируют обработку.
- Сохраняется ограничение существующего inbox/outbox (по 1000 записей), ответ
  ограничен пятью задачами. Это не механизм бесконечного хранения истории.
- Новые таблицы, миграции, scopes, зависимости, внешние endpoints и credentials
  не добавляются. Agent не получает дополнительного права исполнения.

## Проверки и границы

`tests/test_telegram_task_status.py` использует настоящий облачный PostgreSQL и
только HTTP mock. Есть проверки изоляции профиля и подмены ссылки, read-only
полномочий, остановленного admission, одновременного повтора/перезапуска,
истёкшего lease, ложного успеха, разных fence/revision, запрета echo содержимого,
отказов БД/audit/revocation и ограниченной выдачи последних пяти задач.
Некоторые состояния задаются тестовой admin-фикстурой для проверки отображения;
это не доказательство реального исполнения этих состояний.

Существующий сквозной `test_telegram_full_mock_http_cycle` дополнительно
запрашивает статус после настоящего cloud executor/verifier. Отдельный
`scripts/telegram_service_smoke.py` проверяет новые команды внутри ограниченного
service container с actual PG, HTTP mocks и без socket/публикуемых портов.
Полный CI также сохраняет старые restart/watchdog/backup/migration проверки.

Локальная целевая команда: `scripts/cloud_test.sh tests/test_telegram_task_status.py`.
Полный проверочный контур: `scripts/verify_cloud.sh` на чистом commit с образами
того же SHA; не использовать старые local images для доказательства нового кода.

Реальный бот, Telegram-клиент iPhone, VPS rootless/systemd и доставка этой ветки
здесь не проверяются. Ключи, платные AI API, CRM и настоящая публикация PR через
агента остаются отключёнными. Итоговые результаты и ссылка на CI фиксируются
в описании отдельного Draft PR этой ветки.
