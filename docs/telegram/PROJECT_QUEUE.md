# Очереди проектов в Telegram

Облачное продолжение существующих сохранённых запросов и назначения проектов.
База — Draft PR #29, `feat/bounded-vps-operations`,
`b7a32cde4852ad030b3464420bfe12497edc8709`, который сохраняет зависимости
PR #28 и исправленного комплекта PR #17. Ничего не объединяется и не
доставляется на VPS автоматически. Работающее подключение Telegram на VPS
остаётся на прежней версии; новые команды появятся только после отдельного
проверенного обновления.

## Для владельца с телефона

- `/projects` — количество ожидающих запросов по каждому проекту и команды просмотра.
- `/requests lnauto` — последние пять запросов автосервиса и полное количество в очереди.
- `/requests vanilla-sugar` — очередь «Ванили и Сахара».
- `/requests command-center` — очередь AI Commander.
- `/requests capital-lab` — очередь Capital Lab.
- `/requests unassigned` — ещё не распределённые запросы.
- `/requests` и `/requests all` — последние пять запросов всех проектов.
- `/request номер` — полный исходный текст и версия назначения.

Пустой список конкретного проекта явно обозначается. Сначала выполняется
фильтрация, затем выбор пяти последних: более новые запросы другого проекта
не скрывают нужные. Счётчики охватывают все ожидающие запросы текущего
Telegram-подключения, а не только пять показанных. Для назначения проекта
сохраняется существующая команда `/assign номер project-id версия`.

Все запросы остаются `NEEDS_PLANNING`. Это метаданные для организации работы,
не AI-планирование, подключение внешнего репозитория, разрешение оплаты или
запуск бизнес-задач. Голос и настоящий coding provider этой доработкой не
включаются.

## Границы и восстановление

Используются существующие owner/private-chat проверки, профиль подключения,
F1 audit/admission lock, история назначения и очередь ответов. Нет новых
таблиц, миграций, credentials, прав runner или внешних HTTP-операций.
Чужой профиль исключён и из текста, и из счётчиков. Неизвестный фильтр
отклоняется до сохранения запроса; он не превращается в текстовую задачу.

До формирования списка проверяются исходные fingerprints/audit anchors,
привязка назначений и известные секреты всех ожидающих запросов этого профиля.
Повреждённая запись не превращается в пустую очередь другого проекта.
Чтение ограничено 1000 запросами и существующим лимитом истории назначений.
Тексты выводятся как данные, без parse_mode и без исполнения инструкций.

Остановка admission не запрещает чтение и не снимается просмотром. Повтор
того же Telegram Update возвращает прежнюю durable-квитанцию, даже если
назначение уже изменилось. Для свежего списка нужна новая команда. Crash до
commit восстанавливается существующим resume_pending; неопределённая внешняя
отправка не повторяется вслепую.

## Проверки

`tests/test_telegram_project_queue.py` использует настоящий PostgreSQL и
детерминированный HTTP mock. Проверяются фильтрация до limit, полные счётчики,
назначение/снятие назначения, чужие профили и отправители, неизвестные фильтры,
prompt injection, повреждение записи, смена известного секрета, halt,
конкурентный повтор и восстановление после crash.

Существующий container smoke расширен до capture → assign → project counts →
filtered lists → durable replies через fake Bot API и настоящий PostgreSQL.
Это облачный контейнерный тест, не проверка настоящего Telegram/Safari/VPS.
Точные количества и ссылки CI фиксируются в Draft PR этой ветки; результаты
пересекающихся наборов не складываются.
