# Telegram: текстовые запросы и уведомления — облачная основа

## Назначение и зависимость

Владелец управляет центром с телефона: пишет запрос, получает уведомления,
подтверждает чувствительные действия и может остановить работу.
Это продолжение существующих задач, approvals, Outbox и аудита F1.
Ветка `feat/telegram-text-foundation` основана на
`feat/owner-password-login`, PR #20, исходный SHA
`4cc6ec46bf461d65958f013bb23ac2234b9a7fd3`.
Она сохраняет последовательную зависимость от исправленного deployment PR #17.
Слияние зависимых PR и установка на VPS этим изменением не выполняются.

## Что работает в проверяемом контуре

`command_center.telegram_bridge.TelegramBridge` принимает синтетические Bot API
Update, сохраняет их в PostgreSQL и формирует исходящие `sendMessage`.
`MockTelegramHTTP` принимает исключительно `httpx.MockTransport`;
создание клиента с настоящим HTTP transport отклоняется. Значение в URL —
публичная фикстура, не bot token. Реальных Telegram HTTP-вызовов нет.

| Вход | Результат |
| --- | --- |
| Обычный текст или `/task текст` | Запрос `NEEDS_PLANNING`, ответ «запрос сохранён». AI-планирование не подключено; выполнение бизнес-задачи не заявляется. |
| `/demo текст` | Синтетическая задача F1 `approved_render`, затем карточка с точной версией, параметрами, hash, epoch, Git SHA, сроком и описанием эффекта. |
| Кнопка карточки | Одноразовое подтверждение через существующий `Store.approve`. Далее обычный F1 Outbox → Redis → executor → verifier. |
| `/cancel UUID` | Сохранение намерения отмены через F1; принятие команды не выдаётся за доказанную остановку контейнера. |
| `/stop` | Существующий F1 halt: остановка допуска новых задач и отзыв epoch. Автоматического resume нет. |
| `/help`, `/start` | Доступные команды и явное указание ограничений. |

Текст `/demo` ограничен существующим контрактом значений F1: одна строка,
не более 128 символов. Обычный запрос — до 2000 UTF-8 байт; Update — до 8192
байт, ответ HTTP — до 65536 байт. Файлы, голос и пересланные сообщения не
загружаются и не интерпретируются.

GET `/api/telegram/status` и `/api/telegram/requests` доступны только владельцу
через существующую серверную аутентификацию. Первый возвращает отключённую
интеграцию; второй показывает последние 50 запросов, ожидающих планирования.
Отдельный публичный webhook или вход без авторизации не добавлен.
Мобильный Telegram-интерфейс сейчас проверяется как протокол сообщений и
кнопок; работа настоящего приложения Telegram на iPhone этим не доказана.

## Долговременное состояние и безопасность

* `telegram_inbox`: Update ID, профиль владельца/Git SHA, hash нормализованного
  намерения, состояние и связь с F1 task. Повтор Update не создаёт вторую задачу;
  изменение содержимого того же Update ID отклоняется.
* `telegram_cards`: hash случайного nonce, точная версия действия, payload hash,
  epoch, source revision, срок и consumed Update ID. Нужны совпадение привязанного
  владельца, private chat, отправленной карточки и Telegram message ID.
  Срок F1 approval не превышает срок карточки.
* `telegram_deliveries`: durable intent до отправки, `NEW → SENDING → SENT` либо
  `UNCERTAIN`. Сбой/таймаут или перезапуск после возможной отправки не вызывает
  слепой повтор. Уведомление может потребовать ручной сверки; exactly-once
  доставка не обещается.

Существующая блокировка Control и транзакция PostgreSQL сериализуют изменения.
Потребление карточки, F1 approval и ответ владельцу записываются атомарно.
То же относится к фиксации `/cancel` и `/stop` с их ответами.
Аудит связывает hash тела отправки, карточку и подтверждённый message ID.
Нарушение цепочки блокирует обработку. Сообщение об успешном результате требует
совпадения hash артефакта и записи независимого verifier с task/fence/source SHA.
Самостоятельно выставленного `SUCCEEDED` недостаточно.

Предусмотрены ограничения по 1000 inbox и delivery записей, до 20 Update и
отправок за проход. При заполнении обработка прекращается; автоматическое
удаление доказательств не реализовано. Для длительной эксплуатации нужна
согласованная политика архивирования и мониторинга ёмкости.

Секреты текущего runtime и узнаваемые формы ключей отклоняются во входном
тексте. Это не универсальный DLP: нельзя отправлять персональные данные,
клиентские материалы или credentials. Сырые отклонённые сообщения в inbox
не сохраняются. Текст, исходники и ответы инструментов не расширяют полномочия.

## Что остаётся выключенным

* Настоящий Telegram transport, bot token, long-running polling service,
  webhook и `answerCallbackQuery`.
* Доказанная аутентичность реального Telegram Update: ID внутри синтетического
  JSON не является доказательством личности.
* AI-планирование обычного текста, выбор бизнес-проекта, голосовая расшифровка.
* Реальные AI API, GitHub publication и бизнес-интеграции.
* Независимая аварийная остановка через Telegram: `/stop` использует основную
  БД и аудит, поэтому не заменяет внешний административный аварийный канал.
* Автоматическая сверка неопределённых отправок с Telegram: при отсутствии
  надёжного результата необходима ручная сверка, а не повтор.

## Важная граница установки

Добавлены три таблицы и ограниченные права `f1_app`; runtime execution role
не получает доступа к ним. Таблицы создаются только существующим явным admin
bootstrap, не запуском API. Изменились `models.py` и `admin.py`, поэтому текущая
защита deployment **должна блокировать обычное совместимое обновление** старого
VPS bundle. Нельзя обходить fingerprint/migration gate или применять эту ветку
как F31 password-only update. Перед будущей установкой нужны отдельная
проверенная миграция, резервная копия и проверка восстановления/отката.
Эта работа остаётся в облаке до отдельного разрешения.

## Следующий реальный шаг после возвращения владельца к SSH

Сначала завершить уже подготовленный закрытый вход владельца на существующем
VPS. Затем отдельно разрешить подключение Telegram: создать бота без передачи
токена в чат, безопасно инъецировать токен доверенному сервису, подтвердить
Telegram user ID/private chat и проверить отзыв доступа. Реальный transport и
управляемый polling service потребуют реализации и отрицательных тестов;
одного добавления токена для этой ветки недостаточно. Уведомления и команды
должны пройти реальную проверку до заявления о готовом Telegram-управлении.

## Проверки и источники контракта

`tests/test_telegram_bridge.py` проверяет синтетический сквозной цикл с настоящими
облачными PostgreSQL/Redis и Docker executor; собственно Bot API — HTTP mock.
Также проверяются подделка/повтор/просрочка подтверждений, чужой отправитель,
группы, voice/forward, prompt injection, конкурентные повторы, отмена, stop,
повреждение аудита, потеря БД, неопределённая доставка и ложный успех verifier.
Команда: `scripts/cloud_test.sh tests/test_telegram_bridge.py`.
Полный набор: `scripts/cloud_test.sh`; чистая контейнерная проверка:
`scripts/verify_cloud.sh`. Последняя требует образов с точным SHA текущего commit.

Официальные формы Update, CallbackQuery, getUpdates, sendMessage и
InlineKeyboardButton: <https://core.telegram.org/bots/api>.
Используется JSON POST и callback data `tg:` + 32 ASCII-символа (35 байт,
в пределах официальных 1–64 байт). Наличие документации не подтверждает
подключение настоящего бота или гарантированную доставку.
