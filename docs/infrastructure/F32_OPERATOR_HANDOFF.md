## Когда владелец вернётся

1. **Возобновить ограниченный канал.** Одно SSH-подключение владельца; повторно
   использовать установленный runner, не скачивать 217 МБ заново. Свежий GitHub
   registration token вводится скрыто через TTY, не в чат/argv/Git. Runner —
   acc-gh-runner, без sudo/сокетов/секретов приложения. В GitHub проверить Idle.
2. **Явно разрешить подготовку.** После сверки ops HEAD/CI разрешённый commit
   с маркером запуска допускает подготовку. Cloud `verify` должен пройти до
   VPS job. В SSH оператор снимает ограниченный regular-file snapshot bootstrap,
   проверяет новый SHA-256 из таблицы и только затем запускает root bootstrap.
   Старые инструкции с bootstrap 9d2544... не подходят этому пакету.
3. **Дождаться build/inspect receipt.** Root-owned helper запускает сборку от
   acc-control, сохраняет разделение daemon UID 1000/1001, requirements.lock,
   прежние F30/F31 и общий private state. Исходники — `/home/acc-control/f32/source`,
   bundle — `/home/acc-control/f32/bundle`, log — `.../f32/prepare.log`. Приложение
   продолжает работать. Нужен фактический новый bundle digest; не подставлять
   вместо него source SHA, packet hash или bootstrap hash.
4. **Выполнить переход схемы.** Из нового source используется существующий
   `command_center.telegram_transition stage`, с точными old/new bundle digests.
   Stage прекращает приём работы, делает backup и останавливает приложения;
   это реальная пауза интерфейса. Возвращённый конкретный migration plan действует
   15 минут. Его применение — отдельный разрешённый шаг через `apply`, с проверкой
   backup в независимом restore container. Обычный `deployment update` вместо
   этого перехода запрещён разными schema hashes.
5. **Проверить закрытое приложение.** После apply Telegram ещё disabled.
   Postcheck, новый login тем же паролем, сохранность истории, синтетическая
   задача и verifier проверяются на фактическом rootless runtime. Не использовать
   старую cookie как доказательство сохранности входа: source pin меняется.
   Не ставить вручную acceptance flags и не объявлять go_live.
6. **Подключить Telegram отдельным шагом.** Нужны подтверждённый Telegram owner
   numeric ID и токен своего бота. Способ подтверждения ID проверяется при
   подключении; ID не угадывается, чужой бот/случайный адресат не используется.
   Токен вводится скрыто существующим offline provision CLI из нового source,
   в private `.../f30/state/telegram`, не через чат, runner или prompt агента.
   Provision не делает HTTP и не включает бота. Затем готовится отдельный новый
   live bundle с точным connection digest; при той же новой schema возможен
   штатный bounded update, но только после разрешения этого подключения.
7. **Проверить телефон.** Реальный service должен подтвердить getMe/bot ID,
   отсутствие чужого webhook, leader/heartbeat и приём только private owner.
   В Telegram: обычный синтетический текст → номер; `/requests`, `/request номер`;
   `/demo текст` → одно подтверждение → executor/verifier → уведомление;
   `/tasks`, `/status UUID`, отмена/остановка. Посторонний отправитель не получает
   доступ. Не слать клиентские данные или секреты. Windows-окно для дальнейшего
   polling не требуется, но это проверяется после фактического подключения.

Все стадии используют существующий code path. Пароль владельца не пересоздаётся;
public ports, VPN/IdP, платные AI API и производственные CRM не подключаются.
Закрытая веб-панель по-прежнему требует своего доступного туннеля; localhost
Windows сам по себе не является адресом для Safari на iPhone.

## Если результат неопределён

- `attempted`, существующие target paths или FAILED receipt: сначала сверить
  факт выполнения и protected log, не удалять маркер ради повтора и не перетирать
  F30/F31/state. Prepare не является installation receipt.
- Потеря ответа apply: существующий `telegram_transition reconcile`, без второго
  DDL. Неподтверждённый job/backup/audit блокирует продолжение.
- Abort допустим только при доказанном отсутствии DDL. После успешного DDL нет
  автоматического down migration или restore поверх primary; следовать
  существующим ограничениям transition/recovery.
- Неподтверждённый Telegram send остаётся UNCERTAIN, не повторяется вслепую.
  Потеря credential/leader/БД останавливает новые действия.
