# План перехода к облачной разработке AI Command Center

Дата проверки: **26 октября 2026 года**. Статус: **план для проверки владельцем**, не разрешение исполнения следующих этапов.

## 1. Вывод и границы

Разработка AI Command Center уже может продолжаться через облачный Codex и GitHub без Windows, включённого домашнего компьютера и локальных скриптов. В репозитории есть исходники, зависимости с lock-файлами, контейнерные сценарии, CI и инструкции. Переносить разработку на VPS для этого не требуется. VPS нужен для будущих отдельно разрешённых испытаний и эксплуатации, а не для хранения единственной рабочей копии.

Полный переход других проектов пока **не подтверждён**: их исходники, репозитории, зависимости и локальные данные в этом задании не изучались и не загружались. Этот план не даёт Command Center доступ к их production.

Выполнено сейчас: чтение документации и конфигураций, проверка метаданных PR и CI через GitHub, подготовка этого файла. Не выполнялись тесты приложения, установка зависимостей, подключение к серверам, перенос проектов, изменение кода, секретов или настроек GitHub. Старые результаты тестов ниже — исторические свидетельства, не новый прогон.

## 3. Что можно делать полностью в облаке

| Работа | Доступность | Условия и предел доказательств |
| --- | --- | --- |
| Анализ, документация, backend/frontend, ветки, коммиты, PR | Доступно в разрешённой задаче | Нужны доступ к правильному репозиторию и точная база; без merge |
| Ruff, OpenAPI, Python, TypeScript/Vite | Есть воспроизводимые команды и CI | Lock-файлы, поддерживаемые Python/Node и разрешённая установка зависимостей |
| PostgreSQL/Redis, Outbox, API/worker, брокер/watchdog, синтетический цикл | Есть контейнерные проверки | Нужна штатно разрешённая контейнерная среда; её ограничения не обходить |
| Мобильная панель | Разработка, сборка и браузерные проверки в облаке | Сборка не доказывает UX; нужны браузерные тесты и просмотр на iPhone через разрешённый закрытый preview |
| Шифрование копий, тестовое восстановление, отказные сценарии | Проверяемы на синтетических данных | Копия на том же хосте не независима; это не доказательство восстановления реального VPS |
| Реальный coding provider и GitHub publisher | Код адаптеров есть, HTTP-моки доступны | Реальные ключи и внешние операции отключены; mock не доказывает реальный запуск |
| Универсальная разработка других репозиториев агентом | Ещё не подтверждена | F2 ограничен sum_positive_v1/calculator.py и узкой политикой допустимых изменений |
| Rootless/systemd, перезагрузка, реальные ACL/cgroups, VPN/MFA | Только частично моделируются | Окончательные проверки требуют отдельно разрешённой целевой среды |

Сохраняется архитектура: PostgreSQL — источник управляющей истины; Redis — транспорт; транзакционный Outbox; точная Git-ревизия; lease/fencing; независимый verifier; ограниченный broker и watchdog. Облачный Codex сейчас — инструмент разработки проекта, а не доказательство того, что сам Command Center уже умеет автономно разрабатывать любые проекты.

| Шаг | Действие | Зависимость | Проверяемый результат / готовность |
| --- | --- | --- | --- |

| C2 | В отдельной разрешённой документационной задаче актуализировать входные README/AGENTS и текущий статус | C1, ревью плана | Старые ограничения помечены историческими; актуальные полномочия не расширены |
| C3 | Проверить воспроизводимость чистого облачного checkout на exact SHA с lock-файлами | Разрешённая задача проверки, контейнерная возможность среды | CI и доступные локальные проверки привязаны к SHA; пропуски и различия среды перечислены |

| C5 | Подготовить безопасный контекст отдельно выбранного внешнего проекта | Отдельное разрешение на конкретный проект | Инвентаризация, права на код, sanitized-контекст; отсутствующие исходники явно отмечены |
| C6 | После отдельного разрешения перенести только разрешённые исходники и воспроизводимые тесты в отдельный репозиторий | C5, проверка секретов и истории | Чистый cloud checkout собирается и тестируется на синтетических данных без Windows |
| C7 | Сделать изолированное исправление в этом репозитории и PR без production-доступа | C6, конкретный scope | Независимая проверка, понятный отчёт и отсутствие побочных изменений |
| C8 | Рассматривать подключение к Command Center и read-only пилот | C7, совместимый provider/workspace, отдельные разрешения и правовая проверка данных | Проверены allowlist, полномочия, остановка, бюджет, журнал и конкретный пилотный контракт |

Разработка Command Center может идти до восстановления доступа к VPS. C5–C8 не требуют переноса production на сервер центра. Если единственная копия проекта находится на выключенном Windows-компьютере, отсутствующие файлы нельзя получить из облака автоматически: до безопасного экспорта владельцем или уполномоченным сопровождающим доступны только анализ уже предоставленного контекста и подготовка. Владельцу не предлагается выполнять команды на ПК; операция передачи остаётся отдельной зависимостью, пока не появится разрешённый источник.

## 5. Подключаемые проекты

Не открывать чужие репозитории и не менять их в рамках текущей задачи. Сначала отдельное разрешение; каждому проекту — собственный репозиторий, контекст, секреты, тестовые данные и права. Общий пул production-credentials недопустим.

| Проект | Первый допустимый будущий пакет | Блокеры и критерий готовности |
| --- | --- | --- |
| CRM кондитерской «Ваниль и Сахар» | Инвентаризация исходников/стека/интеграций и sanitized-схема данных; затем cloud dev на синтетических fixtures | Локальные файлы и репозиторий не подтверждены. Не обращаться к production-серверу, не переносить CRM на VPS центра. Проверить клиентские данные, локализацию, зависимости и Windows-привязки. Ytimes-чеки и storefront-сделки нельзя учитывать дважды; правила matching не придумывать |
| CRM автосервиса | Только сохранение контекста и перечня отсутствующих материалов | **PAUSED**. Этот план не возобновляет разработку. Нужны отдельное решение владельца о снятии паузы, источник кода и новый scope |
| Capital Lab | После отдельного разрешения — инвентаризация и автономные unit-тесты на синтетических финансовых данных | Исходники и доступы не подтверждены. Будущий пилот предварительно read-only; без брокерских credentials, реальных торговых приказов и финансовых операций |

Порядок реальных подключений не назначается автоматически. Исторический план допускает сначала tentative Capital Lab read-only, затем кондитерскую CRM; автосервис остаётся на паузе. Это не разрешение начинать пилот и не изменение приоритетов владельца.

Для каждого проекта до переноса проверить ОС-зависимые пути, кодировки, регистр имён, зависимости от GUI/COM/Windows-служб, драйверы и лицензии. Обнаруженная Windows-зависимость оформляется отдельной задачей; совместимость с Linux не предполагается заранее.

Предлагаемый комплект в **каждом отдельном репозитории**, без копирования чужих секретов:

| Документ / артефакт | Обязательное содержание |
| --- | --- |
| README.md | Назначение, текущие ограничения, навигация, минимальный воспроизводимый запуск |
| AGENTS.md | Scope, запрещённые действия, команды проверок, права, порядок веток и остановки |
| docs/PROJECT_OVERVIEW.md | Пользователи, цели, внешние системы и границы проекта |
| docs/architecture/ | Компоненты, источники истины, контракты, данные, trust boundaries |
| Реестры требований и решений | Стабильные IDs, источник, классификация, статус, зависимости, критерии проверки; исторические решения не переписывать |
| docs/roadmap/ и docs/STATUS.md | Очередность, активный этап, PAUSED/blocked, точный SHA, PR-базы, незавершённые изменения |
| docs/tasks/ | Scope задачи, acceptance, разрешённые пути/операции, base SHA, лимиты, stop conditions |
| tests/, lock-файлы, CI | Синтетические fixtures, воспроизводимые команды, контракты и неизменяемые acceptance checks |
| docs/VALIDATION.md | Команда, дата, SHA, среда, результат, ссылка на CI; отдельно passed/failed/not run/mock/host-specific |
| docs/security/ и runbooks | Классификация данных, только secret references, backup/restore, аварийная остановка и отзыв |
| docs/HANDOFF.md | Сделано, осталось, блокеры, следующий безопасный шаг и предел полномочий |

Статусы источников сохраняются: OWNER_APPROVED_SUMMARY для исторических сводок; APPROVED для конкретных подтверждённых требований; DERIVED для технических предложений; ASSUMPTION/OPEN/CONFLICT для непроверенного и противоречий. Не придумывать оригинальные даты, IDs или утверждения.

Минимальный handoff одной задачи: project/repository ID → task ID → grant/scope → base SHA → branch/PR base → approved requirements/decision IDs → допустимые пути → лимиты и срок → команды acceptance → результаты с точными SHA → незавершённые внешние intents и резервы → блокеры → следующий безопасный шаг. Ссылки ведут на версионированные документы/CI; длинная переписка не является единственным хранилищем знаний.

GitHub — источник истины для исходников и одобренной документации. В работающем Command Center PostgreSQL хранит задачи, permissions, исполнения и события; GitHub не заменяет БД и её резервирование. Временный облачный workspace не считать долговременным архивом: разрешённые изменения сохранять коммитом и PR, контекст — handoff; секреты и runtime-данные туда не включать.

## 7. Что нельзя переносить в GitHub и AI-контекст

* Пароли, private SSH/TLS/signing keys, API tokens, GitHub App private keys и installation tokens, MFA seeds/recovery codes, cookies, production connection strings и реальные .env.
* Клиентские контакты, переписки, заказы, платежи, документы, production DB dumps, сырые логи, скриншоты и вложения с персональными данными; реальные брокерские данные и credentials.
* Незашифрованные резервные копии, ключи их расшифровки, конфиденциальные audit-артефакты и полные runtime-тома; .runtime, credential-файлы и локальные профили инструментов.
* Код третьих лиц без права публикации/обработки и материалы, для которых не проверены ограничения передачи AI-провайдеру и применимые требования локализации.

Private-репозиторий сам по себе не делает хранение секретов безопасным. В Git — placeholders, синтетические данные, схемы и ссылки на секреты. Значения — через защищённую инъекцию конкретному доверенному сервису, с минимальными правами и отзывом; не через чат, браузерную форму задачи или sandbox агента.

Перед будущим импортом проверять не только текущие файлы, но и всю переносимую Git-историю, LFS, архивы и артефакты. Сначала локальная проверка разрешённого экспорта в изолированной облачной staging-зоне; если найдены реальные секреты — не публиковать, отозвать их по отдельной процедуре, подготовить очищенный экспорт с сохранением происхождения. Простое удаление из последнего коммита недостаточно. Файлы исходной Windows-системы не читать и не загружать автоматически.

## 8. Минимальный процесс с iPhone

1. Владелец открывает облачный Codex с нужным репозиторием, указывает ограниченную задачу, базовую ветку и критерии. Для продолжения — ссылка на PR и handoff; включённый ПК не нужен.
2. Codex проверяет AGENTS, актуальный SHA/PR/CI, scope и доступные возможности среды. Работает в отдельной ветке от правильной кумулятивной базы.
3. Одно разрешение этапа покрывает обычные edits/tests/builds/bounded repairs/commits/PR/report. Агент не просит подтверждение каждой команды, но не обходит обязательную политику платформы.
4. При недоступности Docker или сети агент выполняет независимые разрешённые проверки и честно фиксирует блокер. Наличие SSH-клиента или режима network unknown не доказывает доступность серверов.
5. Агент оставляет PR с описанием, точным SHA, тестами, рисками и CI. Владелец с телефона проверяет краткий отчёт и diff; merge и новый этап требуют отдельного решения.
6. Перед завершением сессии разрешённая работа сохраняется, handoff содержит воспроизводимое продолжение. Незавершённую операцию с неопределённым исходом сначала сверяют, а не повторяют.

Универсальный переключатель «отключить все подтверждения облачного Codex» не подтверждён. Настройки локального CLI нельзя считать настройками облака. Используются штатные разрешения workspace и официальные интерфейсы; обязательный системный запрос не заменяется автоматическим нажатием кнопки. Если нужна настройка среды владельцем, сообщаются конкретная недостающая возможность и поддерживаемый экран/действие только после фактической проверки интерфейса.

## 9. Незавершённые этапы и будущие разрешения

| Направление | Что осталось | Отдельное разрешение / evidence |
| --- | --- | --- |
| Согласование Git-цепочки | Ревью открытых PR, будущий порядок интеграции и branch protection | Merge/изменение GitHub security settings не входят в этот план |
| Первый VPS | Подлинность host key, безопасный credential channel, фактический read-only аудит; затем rootless/systemd/network проверки | SSH, установка и deployment — разные явно ограниченные разрешения; в этом задании нет ни одного обращения к серверу |
